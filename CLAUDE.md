# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
bun run dev          # dev server
bun run build        # production build (also validates TypeScript)
bun run lint         # ESLint
bun run format       # Prettier (write)
bun run format:check # Prettier (check only)
bun run test         # bun test — pure modules, plus callers run for real with the database and the mailer replaced
```

Automated tests cover pure modules (`app/lib/{campaigns,whatsapp,messages,bookings}/`, `app/emails/defaults/`, `app/emails/templates/campaign.test.ts`) and the sending paths (`app/lib/bookings/notify.test.ts`, `app/lib/messages/callers.test.ts`, `app/api/cron/booking-reminders/route.test.ts`, `app/lib/whatsapp/callers.test.ts`), which run the real function with its database, mailer and history replaced through `mock.module` and put the real modules back in `afterAll` (`mock.module` is process-wide). Everything else is validated with `bun run build`, which does NOT validate what hangs off `app/actions/` (a `"use server"` module may only export async functions; never re-export types from one). Those tests that must not hang the suite spawn a child process with a timeout (`app/lib/messages/safe-doc.child.ts`).

**Always run `bun run format && bun run lint` before committing.** Both must pass clean (zero errors, zero warnings).

## Stack

- **Next.js 16** App Router · **React 19** · **TypeScript 5** · **Tailwind CSS v4**
- **next-intl 4** for i18n (EN/ES) with `localePrefix: "as-needed"` — English at `/`, Spanish at `/es/*`

- **Resend** for transactional email

## Key Architectural Patterns

### i18n

Every page under `app/[locale]/(page)/` exports `generateMetadata` using `getTranslations()` from the page's namespace (`messages/en/<page>.json` / `messages/es/<page>.json`). The `meta.title` and `meta.description` keys drive SEO. **Title max 65 chars, description max 155 chars.** A treatment's own page (manual therapies, facials, IV protocols) takes its title and description from its card in the translations; a card whose description runs past 155 in either language carries a shorter `metaDescription` in both, read first by the page, and the card keeps its own text. `app/lib/seo.test.ts` fails if a title or a description of a treatment page is over its limit.

### Database (Insforge SDK)

Two client modes:

- `app/lib/insforge.ts` — anon key, used in Server Components/Actions for user-scoped queries
- `createClient({ anonKey: INSFORGE_SERVICE_KEY })` — service key, used in Server Actions that need admin access (booking mutations, email lookups, Google token storage). Never import `INSFORGE_SERVICE_KEY` in client components.

`authenticate()` (`app/lib/auth-guard.ts`) also answers `verifiedEmail`: the address of the auth session itself, which a user cannot rewrite, unlike `profiles.email`. Any action that chooses WHOSE record to read or change by address uses it (the booking-notice consent in `app/actions/whatsapp-consent.ts` and `save-booking-consents.ts`, and a client's own newsletter preference in `app/actions/newsletter.ts`), never the profile's address.

**Migrations are applied by hand to the one live database** with `npx -y @insforge/cli@latest db query "<SQL>"`, and the CLI has quirks:

- It does not accept `BEGIN`/`COMMIT`: send the statements as ONE string (several statements in one string run in an implicit transaction). The files in `insforge/migrations/` keep their `BEGIN; … COMMIT;` and their comments, so strip both when applying: `npx -y @insforge/cli@latest db query "$(grep -v '^--' FILE.sql | grep -v -E '^(BEGIN|COMMIT);$')"`.
- A string that starts with a `--` comment is read as an option and nothing is applied ("No rows returned"), which looks like success. Always verify with a query to `information_schema` / `pg_constraint` / `pg_class.relrowsecurity` afterwards.
- PostgREST rejects an `or(...)` filter on an UPDATE (it reads the column as one of the table). Read the ids first, then update by id (`retryFailed` in `dispatch.ts` does).
- Postgres does not replace a function whose argument list changed: `DROP FUNCTION IF EXISTS f(old signature)` before the `CREATE OR REPLACE` (as the `upsert_contact` migrations do).
- Every new internal table gets `ENABLE ROW LEVEL SECURITY` and no policies: the service key bypasses RLS, and without it the anon key can read the table. AND `REVOKE INSERT, UPDATE, DELETE ON <table> FROM anon, authenticated` in the same migration, unless there is an explicit reason (written in the file) for a browser role to write it: the schema's default privileges (`pg_default_acl` on `public`, checked 2026-11-24) grant `arwd` (SELECT, INSERT, UPDATE, DELETE) to `anon` and `authenticated` on every new table, so a table whose RLS is ever turned off is writable with the public key at once. Several older tables still lack both; see `docs/plans/2026-11-17-whatsapp-findings.md` (v).
- Every `SECURITY DEFINER` function gets `REVOKE EXECUTE ON FUNCTION … FROM PUBLIC, anon, authenticated` in the migration that creates it, and EXECUTE is granted back only to the role that must call it, with the reason written in the file. Postgres grants EXECUTE to PUBLIC on every new function, and a `SECURITY DEFINER` one runs as its owner, past RLS and the table grants: who may EXECUTE it is the only lock. On 2026-11-24 `admin_set_user_password`, `admin_update_user_email` and `admin_verify_email` (any account's password, address or verification, no check of the caller) were executable by the public key: `20261124_revoke_admin_account_functions` closes them and can be applied at once (no deploy needed). The rest that were open the same day are closed by two migrations that need this branch deployed first: the booking functions by `20261124_bookings_close_browser_writes`, and `check_email_role` (any address's role), `upsert_contact` (any contact, with any consent), `promote_contact_to_client`, `register_for_education`, `register_for_race` (any account or contact, for any event) and `profiles_guard_role` (a trigger: it fires without its caller's EXECUTE) by `20261124_revoke_public_definer_functions`. Their callers are server actions now: the booking form's member check and contact `savePublicContact` (`app/lib/contacts/public-contact.ts`: strict input, rate limited per CALLER only, never per email, so a stranger cannot spend a client's turn and a refusal only leaves the booking without its link; the answer is `member` or not and never the role; no booking-notice consent can be sent; the contact written the public way, see "What a public path may do to a contact"), its promotion to client the last step itself (`confirmPublicBookingCore`, only the booking's own contact), the run and course registrations `registerGuestForEvent` / `registerAccountForEvent` (`app/lib/contacts/event-registration.ts`: a guest by her own contact for an event that exists; a signed-in person herself, by her verified session; only admin and staff another account) and the desk's contact `linkDeskContact` (the team only; admin and staff overwrite, a partner only links or creates). `get_user_role` keeps EXECUTE for `authenticated` because the policies call it as the querying role, always as `get_user_role(auth.uid())`; that migration narrows its body to the caller's own role (`AND id = auth.uid()`), so the role of another account is NULL and no policy changes. Nothing on the browser's side may call `.rpc(` at all: `app/lib/public-definer-functions.test.ts` follows every `"use client"` module's imports and fails if one does, and pins which server modules call each of these functions. A migration that DROPs and re-creates one of them (as the `upsert_contact` ones did) gets PUBLIC's EXECUTE back: it must repeat the REVOKE.
- Applied to the live database and verified: `20261117l` (`whatsapp_suppressed_phones`) and `20261124_revoke_admin_account_functions` on 2026-11-24; on 2026-11-25, after this branch was deployed and the open tabs reloaded, in this order: `20261124_service_tiers_and_settings_rls` (RLS on `service_tiers` AND `service_settings`: everybody reads the active rows, the team all, no browser writes), `20261124_bookings_close_browser_writes` (`bookings` keeps its three read policies, no write policy, no browser INSERT/UPDATE/DELETE, its old write functions revoked), `20261124_revoke_public_definer_functions` (the six functions above revoked from the browser roles, `get_user_role` narrowed to the caller's own role), `20261117m` (RLS on `booking_events`), `20261117n` (the guard on `profiles.email`) and `20261124_bookings_no_overlap` (no bookings overlapped). ROLLING THE CODE BACK to before this branch is now unsafe: the old Settings modal says "saved" and saves nothing, the old booking form writes nothing, the old forms book with no contact linked, and the old Redsys webhook leaves a payment whose hour was taken UNRECORDED. Drop `bookings_no_overlap` first and follow each file's rollback. Each file says in its first line when it was applied.

### Booking Flow

1. Client picks service/date/time on `/booking` → the details step starts a draft through the Server Action `savePublicDraft`, the calendar sets its hour (`setPublicDraftTime`), the last step makes it `pending` (`confirmPublicBooking`) and opens the payment
2. Staff confirms from dashboard → `notifyBooking({ event: "confirmed", …, dateIso })` sends email with Google Calendar button
3. Optional Redsys payment → `/api/checkout/booking-session` → Redsys → webhook at `/api/webhooks/redsys` → `handleBookingPaid()` → confirmation email

**Who writes `bookings`.** Nothing in the browser: `app/lib/bookings/bookings-writes.test.ts` reads the source and fails if a module that runs in the browser (or imports its client) writes the table or calls a function that does, and pins the list of server modules that write it. The public form's three writes are strict Server Actions (`app/actions/public-booking.ts`, logic in `app/lib/bookings/public-booking.ts`): the visitor sends only what she chose (service, session type, professional, day, hour, her details, notes) as a strict object, and any other key (a status, a price, an account) refuses the whole call. The server decides the status (`draft`, then `pending`), the price (`service_tiers.price_eur`, else the centre price), `payment_mode = 'full'`, `location = 'centro'`, the payment note, and the account: `user_id` and `created_by_user_id` are the user of the VERIFIED token (`authenticate`), never an id the browser sends, and a token that does not check out is a guest. A contact id is linked only when that contact's address is the booking's; the session type must be of the service, the professional assigned to it (`staff_tiers`). A draft is rewritten, not duplicated; one past being a draft is left alone (the last step answers `not_draft`, "already confirmed"); one that is gone is started afresh. A booking the server writes for the form is CLAIMED by that browser (`draft-claim.ts`: the id signed with `BOOKING_CLAIM_SECRET`, else the OAuth or service key, in the httpOnly cookie `essentia_booking_claims`, five at most, a day): rewriting, timing, confirming and paying a draft ask for the claim, so a known id is not enough. The last step also checks the day is not past (Canary time), the session type and the service are switched on, and the hour is on the professional's schedule and free (`fetchAvailability`, her own draft excluded); she always gets a professional (the one she chose, or the first one free when she left it to the centre), so the overlap guard covers every public booking. One address gets 10 drafts, 60 hours and 10 confirmations per ten minutes (`createRateLimiter`, a brake in memory) and keeps at most three bookings waiting for their payment (`too_many_pending`); a confirmation that fails or is refused opens NO payment and says so on the step (`confirmFailed`, `tooManyAttempts`). The checkout (`/api/checkout/booking-session`) prices the BOOKING's session type (`bookings.tier_id`, never the body's `tierId`) and opens only on a `pending` booking the browser holds the claim of (`not_open`, `not_yours`): a desk booking (confirmed) or a draft is never charged online. The public «received» email takes only the id and the language from the caller: its content is the booking's row, it goes once per booking, only for a draft or pending booking started or sent to the bank in the last half hour, rate limited, and it never writes the contact. The desk's "New booking" is `createDeskBooking` (`app/actions/desk-booking.ts`, `app/lib/bookings/desk-create.ts`): the team only, strict schema, the price from the session type and the place (a hotel room has the suite price), the duration from the session type, the service's name from `service_settings`, `confirmed`, `created_by_*` from who is asking, and a partner's booking carries her `partner_id` and is never a home visit. Through the service key a partner reaches only her own bookings, as the browser's key let her: every dashboard action on one booking asks `bookingAccess` (`app/lib/bookings/booking-access.ts`: a uuid, the booking there, admin and staff any, a partner only `partner_id` = her, anybody else none) before it reads or writes anything: the edit (`updateBookingByAdmin`), the counter payment, the bonus of a booking (`assignBookingBonus`, `clearBookingBonus`), the client's email (`notifyBooking`, every event but the public `received`), the professional's WhatsApp (`notifyStaffWhatsApp`, only to the booking's professional, or for `unassigned`/`cancelled` to somebody of the team taken off it), the calendars (`syncBookingToCalendars`, `pushBookingToCalendarsAction`) and the desk's history lines; `deleteBooking` is for admin and staff (her screen offers no delete). A partner edits only while the session is more than 23 h 59 min away (`partnerMayEdit`, Canary time through `hoursUntilSession`, judged on the booking as it stands; `partner_window`), the rule her screen always applied; the counter payment and the bonus are not held to it (her screen offers them at any time, the session included). A new action on one booking must ask `bookingAccess` too (`bookings-writes.test.ts` counts them). The history of a booking (`fetchBookingEvents`) asks it too; the list of every contact is admin and staff only, and a partner sees a contact (and its bonuses) only when it is a client of hers (`contactAccess`), with her own bookings only. The edit's payload is a strict schema (`edit-payload.ts`: a calendar day, `HH:MM`, a status and payment of their own), and a partner can neither edit inside the 24 hours nor move one of hers into them; her screens ask the same `partnerMayEdit` (`partner-window.ts`, Canary time). `create_draft_booking`, `update_booking_datetime` and `confirm_booking` are called by nothing any more; `20261124_bookings_close_browser_writes` revokes them from the browser roles with the writes.

**One hour of a professional, one booking.** `20261124_bookings_no_overlap` (applied 2026-11-25) adds the exclusion constraint `bookings_no_overlap` (`btree_gist`): two rows of the same `staff_id` whose `booking_slot(date, time, duration)` ranges overlap (half-open, so back to back is fine) cannot both hold a slot. Holding is every status but `draft` and `cancelled`, with a professional, dated from 2026-11-24 on (one historical pair of 2026-09-23 already overlaps, and history is not rewritten). Drafts are left out on purpose: their 60-minute hold (`holdsSlot`) stays a courtesy of the calendar, and the database arbitrates when a draft becomes a booking, so of two visitors on one hour the first to confirm has it. Every writer maps the refusal (`23P01`, `isSlotTaken` in `app/lib/bookings/slot-taken.ts`) to `slot_taken`: the public form sends her back to the calendar with the hour cleared and «Ese hueco se acaba de ocupar, elige otra hora», and opens NO payment; the desk and the edit screen say the professional already has a booking at that hour; the agents' `create_booking` says it has just been taken. The Redsys webhook, when the money arrives for a booking that did not hold its hour (a draft paid directly, one the cron released) and the hour is now somebody else's: the payment is recorded anyway, the booking stays unconfirmed (no calendars, no confirmation), the history says why (`payload.slotTaken`), a `refund_owed` (reason `slot_taken`) is written as for a duplicate payment, the office gets «Pago recibido para una hora ya ocupada: reembolsar o recolocar» and the client an email in her language (her payment arrived, the hour was taken, the centre will contact her); «Marcar como reembolsado» works on that draft without cancelling it (`refundOpen`), and confirming it on another hour withdraws the refund. An unpaid web booking is released 30 minutes after its payment was LAST opened (its newest `payment/checkout`), not after the form started it. Never roll the code back with the constraint applied: drop it first (the old webhook leaves such a payment unrecorded). A new writer that can put a booking on a professional's hour must handle `slot_taken` the same way (the guard test lists them).

Since 2026-11-24 the only way to pay online is the whole price at booking (`fullPaymentCharge`, less the online discount in `app_settings.payments`): there is no deposit for a new booking, the checkout charges the full price and writes `payment_mode = 'full'` whatever `paymentMode` an old page sends, and the desk never writes `deposit` (`paymentModeFor`); rows booked with a deposit before then still read, show and settle as before. The rule said everywhere (Terms 3.2, the form, the FAQs, the emails, `llms*.txt`): change or cancel up to 24 hours before the session, a cancellation at least 24 hours ahead is REFUNDED (not kept as credit), none within the last 24 hours or for a no-show. Nothing refunds automatically (`RedsysProvider.createRefund` throws): the money goes back by hand in the Redsys portal, and the code keeps the record. The 24 hours are counted on the session's Atlantic/Canary wall clock, winter and summer (`app/lib/bookings/cancellation-window.ts`), never on the server's UTC clock. Every path that cancels (the email link, the dashboard's save through `updateBookingByAdmin`, the assistants' `cancel_booking`) calls `settleRefundOnCancel` (`app/lib/bookings/refunds.ts`, rules in `refund-rules.ts`) after writing the status: a booking with money paid through Redsys (ONLY the webhook's `payment/paid` entries: an order number on the booking proves nothing, since it is written when the checkout starts; desk money and bonus sessions are out) cancelled at least 24 hours before gets a `refund_owed` entry in `booking_events` with the amount and the Redsys order, and the office an email (`staff-refund-owed.ts`, not editable); inside the last 24 hours the client cannot cancel by link, and the team decides: no refund (`refund_waived`) unless they tick "Devolver igualmente" on the edit screen (`refund_late` on the tool); the edit screen records what it showed when "Cancelada" was chosen. A booking that only LOOKS paid online (no webhook entry, or the history unreadable) gets a `refund_owed` entry with `status = 'failed'` (a doubt, never counted) and a "Revisar reembolso" email asking the office to check the order. No column holds the state: it is those entries plus `payment_status`, and the LATEST word decides (`refundState`): a later `refund_waived` (also written when a cancelled booking is brought back) or the `refunded` entries settle an earlier `refund_owed`. A dashboard save that cancels a booking paid online while setting its payment back is refused (`refund_payment_conflict`). The cancel link cancels on a write conditioned on `status <> 'cancelled'` and judges the window and the refund at one moment. The booking page shows the Redsys order number (`bookings.stripe_session_id`), "Reembolso pendiente: …" and, for an administrator, "Marcar como reembolsado" (`markBookingRefunded`: cancelled bookings only, whole cents, never more than is left, conditioned write; the dialog reads "1.000,50" the Spanish way): part of it lowers `amount_paid_eur` (the rest stays income), the rest sets `payment_status = 'refunded'` and `amount_paid_eur` to the TOTAL returned (the ledger shows it as the refund and stops counting it as income; a contact's "Pagado hasta la fecha" skips it, `heldEur`); who, when, amount and note go into the history. The checkout (`/api/checkout/booking-session`) refuses a booking that already holds money (409 `already_paid`, which the form shows as "Esta reserva ya está pagada" on the confirmation page, with no new charge) and opens a NEW Redsys order every time (a reused number can be refused as "pedido repetido" after an abandoned attempt), writing each to the history as `payment/checkout`, so the webhook finds a booking by any order it opened. A second authorised payment for a booking that already holds money (two tabs, an old page) is a duplicate (`judgeArrival`): `payment/duplicate` with both orders, a `refund_owed` tagged `duplicate` on its own order and the office's email; the booking stays paid once and the ledger counts it once; the booking page lists it and an administrator marks it returned on that order (`duplicateOrderId`), apart from the booking's own refund. A retry of either order stays idempotent.

A session drawn from a bonus (`payment_mode = 'bonus'`, owner's rule of 2026-11-24, Terms 3.4) follows the same 24 hours in Canary time: cancelled at least 24 hours before it goes back to the bonus; cancelled later, or a no-show, it is LOST (counted as used). The client cannot cancel that late by link; when the team does, they decide with «Devolver la sesión al bono» on the edit screen (unticked, admins and staff only; `bonus_return_late` on the tool). Every cancel path calls `settleBonusOnCancel` (`app/lib/bonuses/settle.ts`, rules in `cancellation.ts`), which writes `bonus_returned` or `bonus_lost` to the history; no column holds it, the latest word decides (`lostBookingIds`), and the balance reads it through `readBonusUses` (`app/lib/bonuses/uses.ts`), which reports a lost session as status `lost`, counted by `bonusBalance` (`USES_SESSION`). Every reader of a bonus balance (the contact's card, which also shows how many were lost, the booking screens, the MCP contact tool, the over-assignment check) goes through it; a history that cannot be read loses nobody's session. The cancel page promises money back only when some was paid online. The Redsys webhook reads only an authorisation (`Ds_TransactionType` 0) as a payment or a refusal (`classifyRedsysNotification`): a refund (type 3, `0900`) or a cancellation (`0400`) on the same order is logged and ignored, and a refusal never moves a paid booking to `failed`. A payments setting that cannot be read means no online discount (0 %).

### Treatment prices

A price shown to the public is never written in code or in a translation: the centre changes its prices itself (Settings, session types) and a typed figure goes on saying the old one. `cards.test.ts` fails if a `€` appears in `messages/*/{wellness,medicine}.json` or in the data of a treatment or a service page. The files for assistants (`/llms.txt`, `/llms-full.txt`) are not written by hand and are not files: two route handlers (`app/llms.txt/route.ts`, `app/llms-full.txt/route.ts`, `revalidate = 300`) build them from the site's own data (`app/lib/llms.ts`: the bookable services, their treatments, the English names and descriptions, the centre's address), with only what can be booked today, no price (they point at each treatment's page), nothing that is only announced and no treatment whose session type is switched off; never put a `llms*.txt` back in `public/` (`app/lib/llms.test.ts` fails if one is there). A treatment whose session type is switched off in Settings (`service_tiers.active = false`, and none of its names on sale) is HIDDEN from the public site while it is off: no card on its list (the three list pages pass `hiddenIds` to `TreatmentSection`), its page answers 404 (a 404 and not a redirect: it comes back by itself, and a redirect to the list reads as a soft 404), out of both sitemaps, of the files for assistants and of the two agent tools' lists. Which ones is read, never written in code: `listHiddenTreatments` / `isTreatmentHidden` / `listAllHiddenTreatments` (`app/lib/treatments/public-prices.ts`, rule in `visibility.ts`), from the SAME cached read as the prices (one snapshot per service, key `["tier-prices", "snapshot"]`, tag `tier-prices`), so switching it back on in Settings drops the tag and brings everything back with no deploy; a read that fails hides NOTHING (every card, without a price). A treatment with no session type at all is not hidden (a label nobody matched is no decision). Copy that names a treatment says it only while it is shown: a FAQ answer or a session step that names one declares it (`mentions` in `app/data/service-faqs.ts` and in the step of `treatment/data.ts`) and has a wording without it in both languages (`answerWithout`, `descriptionWithout`), picked while it is hidden; the service pages resolve their FAQs on the server (`shownFaqs`, `app/lib/treatments/faqs.ts`) into ONE list for the visible FAQ and its FAQPage schema (in the page's language), and `faqs.test.ts` fails if an answer names a hidden treatment without declaring it. No copy counts the treatments of a service. The cards of `/wellness/manual-therapies` and `/wellness/facial-therapies` and the two agent tools (`list_services` of the MCP server, `essentia_list_services` of WebMCP) take it from `service_tiers`: active session types only, joined to a treatment by name (`sameTreatment`) AND by the length its card shows (`priceOf` in `app/lib/treatments/prices.ts`); the centre's price, falling back to the web one, as the booking form's own list does. No match means no price (the card shows its length alone), never an old one; a card that states no length and whose name has several prices shows none, because the site has no "from" wording with a variable. The read is `listPublicTierPrices` (`app/lib/treatments/public-prices.ts`): anonymous client, `unstable_cache` for five minutes under the tag `tier-prices`, never throws, and a failed read is not kept. The two pages read it on the server, declare the same `revalidate = 300` (a literal; `cards.test.ts` keeps the two figures together) and hand each card its line as TEXT made on the server (`cardLines`), so the price is in the HTML and is not formatted twice by two engines. Each treatment's own page (`manual-therapies/[slug]`, `facial-therapies/[slug]`, `intravenous-therapy/[slug]`) prints the same line under its title, read and made the same way (`metaLine` of `ServiceDetailView`); an IV protocol states its length as a range, so its line is its card's own text followed by the one price its name has (`textWithPrice`). The join by name survives a rename: a treatment answers to its `title` AND to every label in its `tierLabels` (`app/lib/treatments/match.ts`, which also reads `—`, `–`, `-` and `·` as one separator), and the price, the preselection of the booking link and the bonuses all go through `sameTreatment`. The lymphatic drainage was renamed on the site in November 2026 while its session type kept the old label; to rename a treatment, add the old name to `tierLabels`, deploy, and only then change the label in the database (on a deploy without the alias a changed label loses the preselection and takes the treatment's bonuses off sale). Saving a session type in Settings (`tier-modal.tsx`, which also switches one on or off; nothing creates or deletes one) is ONE Server Action, `saveSessionType` (`app/actions/session-types.ts`, a thin door onto `saveSessionTypeCore` in `app/lib/session-types/save.ts`, the ONLY writer of `service_tiers`): administrators only, with the service key, and a strict Zod schema of what that form holds (length in whole minutes, the three prices in whole cents, colour, active; any other key refuses the whole save) plus who performs it (`staff_tiers`: the new ones written first, the removals last, and `null` leaves them as they are). NOTHING writes the table from the browser: it has no RLS yet and the public key could write it, nor its parent `service_settings` (the services), which nothing in the code writes at all and whose deletion cascades to its session types. The action answers within 8 s whatever the database does (`timeout` means "it may or may not have been saved", and the screen says so), and the modal's own wait (`saveWithin` in `tier-save.ts`, 12 s) gives the screen back even if the action never answers, so it cannot stay on "Saving…"; a save that fails keeps the modal open and says why (`dashboard.settings.tiers.errors`). After the write the same call drops the tag with `updateTag` (the Server Action form: the next visit waits for the new price instead of being served the old one once more), and with the tag the prerendered pages that printed it; a test (`app/actions/session-types.test.ts`) reads the source (`app/`, `scripts/`, `i18n/` and the root, `proxy.ts` included) and fails if anything else writes `service_tiers`, `staff_tiers` or `service_settings` (a `from(...)` that is not a read, or the name kept in a variable), if a browser module does, or if the code calls a database function (`.rpc`) that is not on its list of functions read in `pg_proc`; being text, it is a reminder, and the barrier is the RLS. The table's RLS is migration `20261124_service_tiers_and_settings_rls.sql`, which closes `service_settings` in the same file (for each: everybody reads the active rows, the team reads them all, no write policy, and INSERT, UPDATE and DELETE revoked from `anon` and `authenticated`), applied on 2026-11-25 after the deploy. Rolling the code back to `main` now would break the save of a session type in silence (the old modal writes from the browser). A price changed some other way (straight in the database) shows when the five minutes pass. A facial with no `durations` in `services-data.ts` (Kinéa Signature) prints the line written for it in `messages/*/wellness.json` instead. `fetchTreatmentPrices` and `fetchHiddenTreatments` (`app/actions/treatment-prices.ts`) are the same read for the one caller in the browser, the WebMCP tool.

### Email System

All templates are plain TypeScript functions returning HTML strings (no JSX/React Email). `_base.ts` provides `emailBase()`, `bookingDetailsCard()`, `googleCalendarUrl()`, and `calendarButton()`. `sendEmail()` auto-BCCs the admin email fetched from `profiles` table. Always pass `dateIso` (YYYY-MM-DD) alongside the formatted `date` to templates that include the calendar button.

These templates are the **legacy** emails: what goes out when nobody has edited a message. They are not touched by the editor (see "Editable messages").

`notifyBooking` validates and cleans what it is given before sending: it repairs what it can of the payload (an amount as text, a null language or time, an odd phone), cuts and cleans a stranger's text (it is written into an email and a WhatsApp notice) and logs what it refuses; the email still goes. The hourly reminder (`/api/cron/booking-reminders`) stamps `bookings.reminder_sent_at` BEFORE sending and sends only to bookings whose stamp landed, so a failed stamp can never resend every hour; if Resend explicitly refuses the batch the stamp is taken back at once and the bookings are sent one by one in the same run (one bad address no longer costs the others their reminder; a booking refused alone loses its stamp and is retried the next hour, a send whose fate is unknown keeps it and is logged), and with no API key nothing is stamped.

### Campaigns (email + WhatsApp)

Admin-only (`/dashboard/campaigns`). Design: `docs/plans/2026-09-05-email-campaigns-design.md` (email) and `docs/plans/2026-11-17-whatsapp-campaigns-and-editable-messages.md` (WhatsApp and editable messages). Everything not marked WhatsApp below is the email channel.

- Tables `campaigns` (jsonb `audience` + `content`, denormalised counters) and `campaign_recipients` (one row per address or phone; email rows are UNIQUE `(campaign_id, email, cycle)`, WhatsApp rows UNIQUE `(campaign_id, phone, cycle)`). Both have RLS with no policies: only the service key reads them.
- Segmentation runs in `app/lib/campaigns/audience.ts` against `contacts` + `bookings`, never in Resend. Fixed exclusions on email: not subscribed to the newsletter (`newsletter_subscribed` not true: see "Email consent rule"), unsubscribed, no email, `contacts.email_bounced_at` set. Manual picks are unioned with the filter. A SEGMENT (`campaign_segments.conditions`, jsonb) is one of two kinds: a saved FILTER (the default: whoever meets the conditions, today or later; a segment saved before lists existed has neither extra key and behaves as it always did) or a hand-made LIST (`manualIds` + `manualOnly: true`, up to 2000 uuids without repeats, the other conditions stored at their neutral value): only the people picked, whether or not they meet any condition. With `manualOnly` `filterAudience` returns ONLY those ids and every fixed exclusion still applies to them (not subscribed, no address, unsubscribed or bounced on email; the consent of the purpose, STOP, unreachable, a valid phone and the suppression list on WhatsApp): picking someone by hand NEVER skips a consent or an unsubscribe, and a contact deleted since is simply not there. A campaign copies the list with the segment (`SET_SEGMENT`), an appointment notice takes no list (`manualNotAllowed`), and with `segment_entry` a list sends once to its people when the campaign is switched on and never again (no new entrants), the same once-ever rule a filter already has. The segment screen (`/dashboard/campaigns/segments/new|[id]/edit`) shows everyone with an email or a phone in a table (`listSegmentPeople`), filters on screen with the engine's own `conditionsMatch`, and a person picked makes it a list: nobody picked means a filter, and the screen says which in a sentence.
- **Reads go in pages of 1000** (`readAllPages` in `app/lib/campaigns/paged-read.ts`): the database never returns more than a thousand rows however big `range()` is, so one `range(0, 9999)` was quietly short. It does not assume the limit: each page starts where the rows received ended and the read ends only on an EMPTY page. The query must have a total order (the id last); a page that fails fails the whole read, and past 10 000 rows it is an error, never a cut list. In tests, `chainDb` (`fake-db.ts`) cuts a table to the `range` asked, a thousand at most, so a test answers with the whole table and does no paging of its own. The audience's contacts and bookings, a report's rows, the status counts and the suppression list read this way.
- **A run that throws** is not silent: the cron (`/api/cron/campaigns`) writes `[run_failed]` into the campaign's `last_error` (only when it was empty; the first clean run clears it), the report says "the last run failed; it retries by itself". Every marker the engine stores (`[run_failed]`, `[halted]` and `[halted] (<locale>)`, `[unconfirmed]`, `[skipped]` including `[skipped] missing_<locale>`, `template_unavailable: <reason> (<locale>)`, `N sent without being recorded`) is said in words by `report.ts`, with the language when it has one; only text the engine did not mark (Meta's or Resend's own) is shown as it came.
- `dispatchCampaign()` claims the row atomically (`draft|scheduled → sending`), freezes the audience as `queued` rows, sends in chunks of 100 via `sendEmailBatch` with `tags.campaign_id`, `blindCopy: false` and `List-Unsubscribe` headers, and stamps `provider_id`. A resume sends only `queued` rows, so a timeout never double-sends. Each chunk's rows are CLAIMED (`queued → sending`) before the batch goes out, and the batch carries a Resend idempotency key made from the campaign id and its row ids (`chunkKey`; Resend keeps a key 24 h and answers a repeat of the same payload without sending again). A chunk Resend explicitly refused is tried once more; one that got no answer is tried up to three more times (2, 5 and 10 s) with the SAME key and payload, which is safe; if there is still no answer its rows end `failed` with `[unconfirmed] no_answer` and are never resent, the send STOPS there for that run (the rest stays `queued` and the next cron tick resumes it), and `last_error` says so. A row whose `sent` stamp cannot be written stays `sending`, is closed `[unconfirmed] interrupted` after 5 minutes and is counted apart (`N sent without being recorded`, said in the report). `retryFailed` never requeues `[unconfirmed]` or `[skipped]` rows and answers `nothing_to_retry` when nothing is left to requeue; resending an unconfirmed chunk by hand means checking Resend and using a hand-made segment.
- The Resend webhook (`/api/webhooks/resend`) routes events carrying `tags.campaign_id` to the `record_campaign_event` RPC, which moves a recipient forward only and bumps counters once. Opens/clicks need tracking enabled on the Resend domain and the events subscribed on the webhook.
- Email body is a Maily document (`@maily-to/core` editor in the content step, `@maily-to/render` on the server). `campaignEmail()` wraps the admin's document between our logo and the fixed footer and renders the whole thing with Maily; plain `{{first_name}}` text tokens are filled afterwards (escaped), Maily variable nodes by the renderer. House templates are still written as simple blocks in `app/lib/campaigns/templates.ts` and converted with `blocksToDoc()`.
- **Languages: a campaign is written in every language its audience includes, and each contact gets the version of her own** (`app/lib/campaigns/languages.ts`, pure). `audience.language` decides which versions exist (`requiredLocales`): `any` needs BOTH `es` and `en`, `es` or `en` only that one (the other is not on the form and nothing is asked of it). It is the language condition that decides, not who is in the audience today: an automation writes to whoever qualifies later, and a hand-made list has its conditions at their neutral value, so it needs both. A draft may have a version half written; sending, scheduling and activating may not: `scheduleCampaign`, `sendCampaignNow` and `activateCampaign` hold the SAVED row to the full rules (the list does all three to a draft without the form) and answer `missing_es | missing_en | missing_both`, `errors_es | errors_en | errors_both` or `missing_es_errors_en | missing_en_errors_es` (`incompleteError`: a version is MISSING when a field it needs is empty, and has ERRORS when it is all written but something is wrong, a subject past its limit say), and the form's toast says the same. Each recipient row carries the language she is written to in (`recipientLocale`, set when the audience is resolved): the contact's `preferred_language`, read as the language filter and the counts read it (only `es` is Spanish; English, nothing or anything else is English), or the audience's own when it fixes one, hand-picked contacts included. The email sender picks `content[language]` row by row (subject, A/B subject, body and the unsubscribe page of that language), so one send mixes both; a row whose version has no subject or no body (an older campaign written for one language, say) is never sent an empty email: it ends `failed` with `[skipped] missing_<locale>` (unclaimed, never requeued by `retryFailed`) and the other rows go out. `audience.sendLocale` ("one language for everybody") is OBSOLETE: accepted so an old row still reads, it decides nothing and the form drops it. In the form, "What it says" has a switch Español | Inglés over the subject (`components/dashboard/locale-tabs.tsx`; the page of a message in Settings has links instead, its languages being two pages) that changes subject, preheader, title and body at once and marks the version with something missing; the preview and "Send me a test" are of the version on screen (`sendTestCampaign(…, locale)` sends that one email); a starting point (a house template, a previous campaign) writes BOTH languages (`starting-content.ts`; every house template has both, a test validates each as a campaign for everybody); an A/B test has its two subjects in each language, its recipients are dealt A and B alternately WITHIN each language (`dealVariants`) and its report shows each variant language by language (`variantBreakdown`). The email editor hands its words to the form a beat after the last keystroke (`_form/editor-flush.ts`): the language switch, the step's confirm and the step folding away write them first, to the language they were typed in, and the confirm judges the form with them (`contentVerdict` in `_form/form-actions.ts`, where the form's other decisions live as plain functions); the preview shows only the version of the language on screen (`preview-state.ts`). The review and the report say how many recipients go in each language (from the rows).
- **Kinds**: `standard` and `split` (A/B subject, recipients dealt alternately within each language, per-variant and per-language opens in the report) are one-off sends. `automated`, `autoresponder`, `rss` and `dateBased` are `active` campaigns: every cron tick `runAutomation()` resolves the segment, asks `automation-rules.ts` who is owed an email today and under which `cycle` (`""` once ever, the year for birthdays, the post id for blog announcements), inserts `queued` rows (unique on `campaign_id, email, cycle`, so repeats are no-ops) and sends them. Triggers: `newsletter_subscribed`, `segment_entry`, `after_booking` (+days), `birthday` (needs `contacts.birthdate`), `first_booking_anniversary`, `new_blog_post` (template vars `{{post_title}}`, `{{post_excerpt}}`, `{{post_url}}`).
- **Appointment notices** (`kind = 'appointment'`, WhatsApp only, `kindAllowedForChannel` refuses it on email): a notice to a client about her OWN booking, set as an automated campaign so the admin can have several (48 h before, 2 h before, 24 h after the visit…), each with its own template and parameters. The trigger is `before_visit` (`hours` 1–336 before a booking STARTS) or `after_visit` (`hours` 1–720 after it ENDS); the schema refuses those events on any other kind, and `manualIds` on this one (its audience is the appointments, nobody is added by hand). The rules (`automation-rules.ts`) count EVERY confirmed booking of the client (`after_visit` also completed ones), with `cycle` = the booking id, so the unique index `(campaign_id, phone, cycle)` makes it one notice per booking and campaign however many runs see it; a campaign limited to some services filters the BOOKINGS, not the client. They are NOT retroactive: a booking is due only from `start − hours` (or `end + hours`) on, and only if that moment is not older than `activated_at`, so switching a campaign on never fires a burst for the bookings already inside its window. Hours are instants (the clock change moves nothing); a booking with no time starts at the day's first moment in the Canaries. The message's `vars` are that booking's `service`, `session_type`, `date` and `time`. It is evaluated by the campaigns cron (every 15 min), so a notice can arrive up to 15 minutes after its moment, and it has a LATENESS BOUND (`GRACE_BEFORE_MS` 45 min, `GRACE_AFTER_MS` 3 h in `automation-rules.ts`): past it the notice is LOST, not sent late. That is deliberate: without it a booking confirmed 30 minutes before it starts would set off every 48 h, 24 h and 2 h campaign at once, and a campaign paused for days would send the arrears on resume. If the cron is down for longer than the bound the reminder is lost (the instant confirmation covers last-minute bookings). A notice still `queued` when it is no longer in its window, or whose booking is gone, is closed `failed` with `[skipped] late` (not sent, and a retry leaves it alone). The appointment notices run FIRST in every cron tick (`cron-plan.ts`), before a one-off send can use up its time. The cycle is the booking id, so RESCHEDULING a booking does NOT resend the notice. A campaign of this kind is switched on, never sent: `sendCampaignNow`, `scheduleCampaign` and `dispatchCampaign`'s preflight answer `locked` for every kind in `AUTOMATED_KINDS`. For this kind the bookings are read from the last 31 days on, in a fixed order. Bookings are folded into `Recipient.appointments` (`visits.ts` `foldAppointments`) only when `runAutomation` resolves this kind (`resolveAudience(..., { purpose: 'appointment', appointments: true })`); the audience preview takes the kind as its optional fourth argument for the same reason.
- **Consent by purpose** (`ConsentPurpose`, `consentPurposeOf(kind)`): an appointment notice is TRANSACTIONAL, so its audience and the per-batch recheck in `dispatch-whatsapp.ts` need `whatsapp_opted_in_at` (the booking notices), NOT `whatsapp_marketing_opted_in_at`; every other WhatsApp campaign is the other way round. The opt-out, the unreachable mark, a valid phone and the STOP list (`whatsapp_suppressed_phones`) apply to both. A contact with the wrong consent is `[skipped] no_consent`. Email has no purposes and is unchanged. Bookings the team creates from the dashboard record no consent, so those clients get no appointment notice until it is switched on in their card.
- **Email consent rule**: an EMAIL campaign reaches ONLY contacts subscribed to the newsletter (`newsletter_subscribed = true`), and of those not one who unsubscribed (`newsletter_unsubscribed_at`) or bounced. Every email kind is news and offers (`consentPurposeOf` gives an email kind no other purpose), so it needs that yes, as a WhatsApp campaign needs `whatsapp_marketing_opted_in_at`. It is a fixed exclusion of the email channel in `filterAudience` (`contactPoint`), NOT a condition: there is no override per campaign (decided 2026-11-24: the law asks for the contact's consent, and it is hers, not the campaign's), a hand-picked contact and a hand-made list need it too, and the segment's "Subscription" filter only still narrows a WhatsApp audience. Before every chunk the email sender reads the three columns again (`emailConsentVerdict` in `dispatch.ts`): a contact who unsubscribed, is not subscribed, bounced or was deleted since the audience was frozen fails as `[skipped] opted_out | no_consent | bounced | no_contact` and is never requeued; one the read did not return stays queued; a read that fails stops the send. Every count (the audience step, the segment picker and pages, a segment's members) is the resolver's, so it is the subscribers; the screens say so (`audience.reachEmail`, `reachEmailNote`, `segment.everyoneEmail`, `segments.countNote`, the review's "Newsletter subscribers only"). The newsletter checkbox/toggle (booking form, sign-up, dashboard new contact + new booking) only ever sets `newsletter_subscribed = true`; unticked means "do not touch". `upsert_contact(p_newsletter)` encodes this for the team, `writeContact` for the public paths. An explicit unsubscribe stamps `contacts.newsletter_unsubscribed_at`, and the audience resolver excludes those contacts whatever the campaign's filter says. No form takes it back (owner's decision of 2026-11-24): the booking form, the footer's form (`subscribeUnlessUnsubscribed`: an unsubscribed address stays off, with the same answer as any other) and the sign-up leave it; only her account's preference and the centre's switch do.
- **WhatsApp channel**: `campaigns.channel` is `email | whatsapp` (CHECK). Same engine, same cron tick (`/api/cron/campaigns`, every 15 min). `split` (A/B subject) and `rss` are email-only (`kindAllowedForChannel` in `whatsapp-form.ts`). A WhatsApp send is an approved Meta template plus a mapping of its `{{n}}` parameters, ONE PER LANGUAGE the campaign is written in (Meta keeps each language of a template as a template of its own): `content.whatsapp` is `{ es?: { templateId, params }, en?: { templateId, params } }`, each parameter a contact/booking field or a static text, and each row goes out with the template and the parameters of ITS language. The appointment notices too: a notice for every client needs a Utility template in each language. A block saved in the old shape (`templateId` + `params` with no language) is still accepted by the schema and read by `whatsappBlocks` (`whatsapp-content.ts`) as the template of the language that campaign was sent in (`legacySendLocale`: the audience's, else its old `sendLocale`, else Spanish), which leaves the other language missing; the form loads it into the new shape and only writes that. In the form the same switch as the email changes template, parameters and preview, and picking a template in one language proposes the one of the same NAME in the other when that one has none yet (`counterpartTemplate`); the test is of the template on screen (`sendTestWhatsAppCampaign(…, locale)`). Error keys are `content.whatsapp.<locale>.templateId` and `.params`.
- **WhatsApp templates**: table `whatsapp_templates` (RLS, no policies), a local copy of the account's Meta templates; Meta owns the status. `syncTemplatesFromMeta` (`app/lib/whatsapp/sync-templates.ts`) reads `/{WABA_ID}/message_templates` (needs `WHATSAPP_BUSINESS_ACCOUNT_ID`) and writes the copy; NOBODY syncs by hand: the templates card runs it in the background when it comes near the screen and its copy is more than ten minutes old (the card says when, under its New template button: "Updated 3 min ago", relative, redrawn every minute, the exact date in the tooltip) (`shouldAutoSync`, through the admin-only action `syncWhatsAppTemplates`), and `/api/cron/whatsapp-templates` runs it every hour, so a status the webhook never delivered or a template made in Meta's own manager still arrives. `createWhatsAppTemplate` submits one, and the webhook's `message_template_status_update` moves `status` (`draft | PENDING | APPROVED | REJECTED | PAUSED | DISABLED`). Only a template with `status = 'APPROVED'` AND `unsupported_reason IS NULL` is sendable. `unsupported_reason` is set at sync for what the dashboard cannot fill: `media_header`, `header_variable`, `named_params`, `button_type` (a URL button with a variable suffix). Its language must be the one of the version it is chosen for (`es_ES` serves `es`): a Spanish template is not a choice for the English version. Placeholders are `{{1}}…{{50}}`, consecutive, never at the start or end of the body (`app/lib/whatsapp/templates.ts`). A campaign cannot be activated or scheduled with a template that stopped being sendable (`templateGate`), in ANY language of its audience: the gate, the dispatch's preflight and a full save check the template of each (`campaignTemplateIssue`), and the refusal carries `detail` (the reason) and `locale` (whose template).
- **WhatsApp recipient rows**: `email` is NULL, `phone` is E.164 (`toCampaignPhone`: `toE164` plus the CHECK `^\+[0-9]{8,15}$`; a contact whose number does not fit is left out), `language` is always set, and `CHECK (email IS NOT NULL OR phone IS NOT NULL)`. The audience is deduplicated by phone (two contacts with one number would break the unique index) and excludes a contact with `whatsapp_unreachable_at`.
- **WhatsApp sending** (`dispatch-whatsapp.ts`): the templates of the languages present in the queue are read once per invocation (`loadCampaignTemplates`), and a language whose template cannot go out right now (paused, missing, wrong parameters) holds ITS rows `queued`, unclaimed, with `template_unavailable: <reason> (<locale>)` in `last_error`, while the rows of the other language still go out: an English template Meta paused does not cost the Spanish clients their notice. The audience is frozen as `queued` rows, then each row is CLAIMED with a conditional `UPDATE queued → sending` that stamps `claimed_at`, and written the moment Meta answers, so a killed process never leaves a message sent twice. A row left in `sending` for more than 5 minutes becomes `failed` with `[unconfirmed] interrupted` (it may have gone out). One shared deadline of 50 s per invocation (`deadline.ts`), 10 messages a second, 45 s of sending: at most 450 messages per cron run (`WHATSAPP_MESSAGES_PER_RUN`); what is left stays `queued` and the next tick resumes it. Before EVERY batch the consent and the suppression list are read again: a row whose contact opted out, never consented, is unreachable or is on the list is not sent and ends `failed` with `[skipped]`. A suppression list that cannot be read stops the send with the rows still queued. After 3 whole batches refused by Meta for the same reason it stops: a one-off campaign becomes `failed` and an automation `paused`, with `last_error` starting `[halted]`. `retryFailed` requeues failed rows except `[unconfirmed]` and `[skipped]` ones. An automation is also stopped after three refusals in a row for one reason from the account or the template, counted across cron ticks over the last 48 h (`refusalStreak`); a refusal that is about the recipient (a number with no WhatsApp) never counts, in either rule. Both rules count PER LANGUAGE of the rows (a language's share of a batch is its batch; `refusalStreak(…, locale)` reads that language's rows): the Spanish messages that go out must not hide that Meta refuses the English template every time. What happens then is `haltDecision` (`language-halt.ts`, pure): in a campaign written in two languages, the stopped language is HELD, not the campaign: its rows stay `queued`, unclaimed, while the other goes on (the same rule as a template the local copy calls unsendable), and `last_error` is `[halted] (<locale>) <reason>` (`haltMessageIn`), which every run writes again and the next run reads back (`heldLocale`). The campaign stops whole (one-off `failed`, automation `paused`) only when every language it is written in is stopped, or, a one-off, once nothing but held rows is left; a campaign in one language stops as it always did, with `[halted] <reason>`, and so does one whose two languages Meta refused for the same reason (the account). The hold is lifted by a person: switching the automation off and on (`activateCampaign` clears `last_error`) or retrying the one-off (`retryFailed` clears a `[halted]` mark when it reopens); if Meta still refuses, the streak already on the rows holds it again at the first refusal. A one-off's preflight judges every language of the audience on a FRESH send (any that cannot go out blocks it); on a RESUME only the languages still queued, blocked only when none of them can go out (the sender holds the rest); on a RETRY the languages of what it would send (queue and requeued failures), any of which blocks it.
- **WhatsApp events**: the webhook (`/api/webhooks/whatsapp`) hands Meta's states to `record_campaign_event` as Meta names them (the function maps `read` to opened and `failed` to bounced for WhatsApp rows, and a failure's Meta error code is stored in `error`). Code `131026` (no WhatsApp on that number) stamps `contacts.whatsapp_unreachable_at`; `131049`, `131048` and the other rate or spam codes are transient and do not. Any inbound message from a number clears that stamp.
- **WhatsApp consent rule** (three columns on `contacts`, two purposes because the law and Meta separate them): `whatsapp_opted_in_at` = the booking notices (confirmation and reminder of the appointment: transactional); `whatsapp_marketing_opted_in_at` = news and offers (campaigns and automations); `whatsapp_opted_out_at` = ONE global opt-out from a `STOP` or `BAJA` reply (exact word; `CANCELAR` is deliberately not one) that blocks both. The public booking form has TWO checkboxes and no WhatsApp box of its own: (1) the required "I accept the Terms and the Privacy Policy, and that you send me my booking confirmation and reminder by email and WhatsApp" IS the consent for the booking notices; after the details step `saveBookingConsents` stamps `whatsapp_opted_in_at` (only on a contact written in the last 15 minutes that has no consent and no STOP and whose phone is the one typed in the form, and a signed-in client's address comes from her verified session), and it never lifts a STOP, so booking again does not reactivate a BAJA; the required box is never restored ticked from `localStorage`, so an abandoned booking comes back on the details step at the latest (`resumeStep`) and `confirmBooking` refuses to go on to the payment without it (`incomplete`: back to the details, with the error); her own contact is written only when the address in the form IS her session's (`consentTarget`): with another address in it (a booking for somebody else, staff with their session open) the name and phone typed never reach the session's contact, profile or newsletter, the step has the server write that other person's contact as it does a guest's (`savePublicContact`, `bookingForSomeoneElse`) and the consent of that booking follows the guest's path, with the same guards; (2) "news and offers by email and WhatsApp", the only box that is not required (the Terms box carries the red asterisk), is ONE choice that sends `p_newsletter` and `p_whatsapp_marketing` together. Bookings the team creates from the dashboard record NO consent, so without one there is no WhatsApp notice. **What a public path may do to a contact** (owner's decision of 2026-11-24; `writeContact` in `app/lib/contacts/write-contact.ts`). A public path is any that proves no address: the booking form (a guest, someone booking for another person, AND a signed-in client's own session), the run and course registrations, a bonus bought online, the footer's newsletter form and the sign-up. It CREATES a contact that does not exist with what was typed, as always. An EXISTING contact keeps its name, phone, language and gender, whatever was typed (the booking row keeps what was typed, and the team sees it there); it only GAINS a yes the person gives ("news and offers": the newsletter and WhatsApp marketing), and never over a no: a STOP (`whatsapp_opted_out_at`) and an unsubscribe (`newsletter_unsubscribed_at`) stay, ticked or not, so a client who left does NOT get her notices or the news back by booking again (until 2026-11-24 the news tick lifted the STOP; pinned now in `self-consent.test.ts`). Coming back is a reply on WhatsApp handled by the centre, her own account's newsletter preference (`updateNewsletterForUser`, her verified session) or the switches on her card. The booking-notice consent is never a public path's to give except through `saveBookingConsents` with its guards, one of which is that the contact's phone IS the phone typed (E.164), so a stranger who types a client's address with her own phone gets no consent for anybody's number. The team's confirmation of a booking and a paid web booking only LINK the contact (`link`: found, or created with the booking's details; a lead made a client with `promote_contact_to_client`, a member stays a member), never rewrite it with what the form typed. Only admin and staff, at the desk and through the agents' `create_booking`, overwrite a contact (`upsert_contact`, as before); a PARTNER at the desk links an existing contact or creates a new one and changes nothing of an existing one, its subscriptions included. The consent writes of the step are ONE server action (`saveBookingConsents`, a thin door onto `saveBookingConsentsCore` in `app/lib/whatsapp/save-booking-consents.ts`, which takes the deadline as a parameter so a test can shorten it and the browser cannot; logic in `app/lib/whatsapp/booking-consents.ts`) that the form calls last and does not await, and the time limit is INSIDE it: every read and write races one 3 s deadline (`BOOKING_CONSENT_DEADLINE_MS`), and when it is up the action answers `timeout` without throwing and BEGINS nothing more. What was begun is finished: the deadline is not looked at between her contact and the notice consent (a contact written and left unstamped is a booking with no notices), and work still running at the deadline is handed to `after()` of `next/server` (`keepAlive`), which holds the function open until it settles or `BOOKING_CONSENT_GRACE_MS` (10 s) passes. A timer in the browser would protect nothing: Next runs a page's server actions one at a time, so a hung action holds up the ones queued behind it (the calendar's availability, the confirmation) whatever the browser stops waiting for. The read the form makes on arrival (`fetchOwnMarketingOn`) is under the same limit. A lost write only costs the WhatsApp notice. The action is public (a guest has no session), so: its input is validated before anything is read; its answer has ONE shape, `{ ok, error? }` (`publicReply`), and never says whether a consent was stamped (that would tell a stranger an address has a contact that was just written); one address gets 30 calls in ten minutes (`createRateLimiter`, in the memory of the instance: a brake, not a guarantee); and "her session's address" is `verifiedEmail` of `authenticate()` (the auth session's own address), never `email`, which prefers `profiles.email` and a user can rewrite her own profile. Like the newsletter, the boxes only ever turn a use on; unticked means "do not touch" (`null`, never `false`). `upsert_contact(p_whatsapp, p_whatsapp_marketing)` encodes it for the team's paths (a public path never clears an opt-out: `writeContact`): ticking a use clears the opt-out; stamps the date only if it was empty, EXCEPT after an opt-out, where it stamps a fresh `now()` and sets the OTHER use to NULL (a consent given before the STOP must not come back to life on somebody's click). `app/lib/whatsapp/consent.ts` does the same in TypeScript; keep the two in step. The form's consent lines live in `messages/*/booking.json` (`detailsStep.consentNoticeSuffix`, `newsletterOptIn`); `consentSuffix` stays plain because the bonus checkout reuses it. "News and offers" is ONE consent for email and WhatsApp everywhere it can be set from the team's side too: the contact page (`/dashboard/contacts/<id>`) has TWO switches that save at once, "Appointment notices" (`setWhatsAppConsent`, `whatsapp_opted_in_at`) and "News and offers" (`setMarketingConsent`: turning it on subscribes the email and consents WhatsApp marketing together, reusing `whatsappActivationPatch` for the STOP rule, and clears the contact's own `newsletter_unsubscribed_at`; turning it off withdraws both and stamps NEITHER `newsletter_unsubscribed_at` nor the global STOP, which only the contact causes, and then updates the Resend list). Its state is `marketingRowState` (`on` only with both channels and no STOP; `email_only` / `whatsapp_only` for older data show the switch off and turning it on completes the other channel; `opted_out` for a STOP). Turning either on asks for confirmation. The old "Newsletter" row of the details form (the one tied to Save) is gone, but the new-contact and new-booking screens keep their own newsletter switch. How to opt out is NOT written under the boxes: it is in the data-protection panel of the form (`detailsStep.optOutValue`: the unsubscribe link of each email, BAJA/STOP on WhatsApp) and in the Privacy Policy.
- **Suppression list** (`whatsapp_suppressed_phones`, migration `20261117l`): a STOP also writes the sender's NUMBER here, whether or not a contact matches it, because the booking form stores any phone typed with the box ticked and so cannot prove whose number it is. Nothing a form, a checkbox or `upsert_contact` does removes a number: only an administrator, from the contact's card. Every reader fails closed: until the migration is applied no WhatsApp message to a client or in a campaign is sent. Email never reads it.

### Editable messages

The transactional emails to a client (`booking_received`, `booking_confirmed`, `booking_paid`, `booking_rescheduled`, `booking_cancelled`, `booking_reminder`, `consent_request`, `bonus_purchase`) can be edited from Settings: the list is the "Automatic messages" card (`/dashboard/settings#settings-messages`) and each message has its own page (`/dashboard/settings/messages/email/<key>/<locale>`); it is not in the sidebar, and every address lives in `app/lib/messages/message-route.ts`. The staff notice, the account lock emails and the contact form are NOT editable. Inventory with every email's current text, callers and parameters: `docs/plans/2026-11-17-message-inventory.md`.

- `message_templates` (RLS, no policies): one row per `(key, channel, locale)`, UNIQUE. `channel` is `email | whatsapp`; the email row holds `subject`, `preheader` and `doc`, the WHOLE email as one Maily document (its `title` column is only read from rows saved in the old shape; new rows leave it NULL); the WhatsApp row holds `whatsapp_template_id` and `whatsapp_params`. The catalogue of keys lives in code (`app/lib/messages/catalog.ts`: variables, fixed blocks, `whatsappEligible`), not in a CHECK. `message_templates.enabled` is the SWITCH of that row (see below).
- **No saved row means the email that has always gone out, byte for byte.** Every sender asks `renderMessageEmail()` (`app/lib/messages/render.ts`) and gets `{ kind: "legacy" }` (use the `app/emails/templates/*` function exactly as before), `{ kind: "custom", subject, html }` (the admin's version) or `{ kind: "skip" }`. Anything that goes wrong (database unreadable, render throws) is `legacy`, never "send nothing" and never a broken email. A row that carries no text of its own (only the switch, or a body that is not a usable document) is not an edit: legacy.
- **Every message has a switch** (`enabled` of its row, per `(key, channel, locale)`; no DDL). It is the admin's decision, taken knowing what it stops: the list of Messages has one switch per row (message and channel) that writes BOTH languages through `setMessageEnabled` (an admin's action: it validates key and channel against the catalogue, writes the switch and NOTHING else, no author or date of an edit; turning off is an upsert, turning on only updates rows that exist, so no row is ever created to say "on"). Turning OFF asks first in `confirm-dialog.tsx` with what it will stop, message by message (`switch.offDialog.body.<channel>.<key>`); turning ON does not. Saving a text never changes the switch (`saveMessageTemplate` drops `enabled`), and a reset keeps an off row off (emptied, not deleted, both channels). No row is on, and a row with only the switch is not an edit: on, the email is the one that has always gone out, byte for byte. A row whose languages disagree (old data) is shown off, names the language, and a press turns both on. Off, `chooseDelivery` answers `skip` for ANY key, and EVERY sender must send nothing, throw nothing and leave it written down: `notifyBookingCore` and the cancellation by link and the paid confirmation write a `skipped` entry (`error = "message_off"`, summary from `off-note.ts`) in the booking's history and carry on with the rest of the event; the voucher logs a warning (it has no booking history); the reminder cron logs one warning with the count and stamps nothing; the consent request sent by a person answers `message_off` BEFORE creating a link or reopening a signed consent (`isMessageOff`), and the contact page says "this message is switched off in Messages"; the client's WhatsApp is a decision `off` (judged before the template, only for a client who WOULD have been messaged) with one entry that says it is off, never the configuration `skipped`. A switch that cannot be read is not a switch: the email is sent (fail open towards the email that has always gone out). The test button of a message's page still sends to the admin's own address: it is a preview, not a send to a client. A new sender must handle `skip` the same way, and a test per sender pins it.
- **The whole email is one document** (`app/lib/messages/email-doc.ts`, pure). Besides the editor's own nodes it has three, ONLY at the top level (never inside a section, column or list): `emailKicker` (the small line in capitals ABOVE the title, e.g. "Booking confirmed": the same inline text and variables as the title, no marks, no attributes, at most one, FIRST when present, and it may be empty, in which case nothing is printed; the editor always keeps an empty one first as the place to write it and `sameDoc` ignores an empty one), `emailTitle` (inline text and variables, no marks, exactly one, kept first by the editor) and `systemBlock` with `attrs.kind`, one of the blocks the catalogue lists for THAT message (`details_card`, `location`, `payment_note`, `calendar_button`, `cancel_link`, `consent_button`, `bonus_card`), nothing inside it, each kind at most once. The order of the editor is the order of the email: kicker, title, text, blocks. The catalogue says which blocks are `required` (`FIXED_BLOCK_INFO`): the cancellation link, the consent button, the payment notice and the voucher card are what an email MUST carry; the booking details, the location and the calendar button may be left out without a word. In the editor every block can be moved, removed and put back.
- **Composing** (`composeMessageEmail` in `compose.ts`, the one composer): the same shell as the legacy email (`emailBase()`, or `booking_paid`'s own HTML), then the top-level nodes in order. A run of the editor's own nodes is sanitised and drawn by the renderer; the kicker and the title in the style the email has always had (`KICKER_STYLE`, `H1_STYLE`, byte for byte as the legacy templates print them; an empty kicker prints nothing); each block by the code from the booking's data (`fixedBlocksByKind` in `fixed-blocks.ts`, by kind, handed over by the caller as `blocks`). A block whose condition does not hold (nothing owed, no link, consent already signed) is "" and prints nothing. Before drawing, `repairForSending` puts the default title first when there is none, keeps the first title only, keeps the first kicker only and moves it to the very top if it was found elsewhere (never lost), cleans both to text and the message's variables, drops a block of another message, a repeated one or one with content, and ADDS at the end any required block that is missing: no email goes out without them. Saving (`schema.ts`, `structureProblems`) refuses all of that, naming the block that is missing (`doc.blocks.<kind>` = `blockRequired`, `doc.title` = `titleOne`), an empty title (`doc.title` = `titleEmpty`: no text but spaces and no variable) a title or kicker with attributes or anything but text and the message's variables, more than one kicker (`doc.kicker` = `kickerOne`) or one that is not first (`kickerMisplaced`); and at send a title that comes out empty after the variables (a variable with no value for that booking) is the message's default title, never an email without its heading. Saving a body also sets the old `title` column to NULL (unless the caller sends one), so an old row cannot come back as custom with its old title. All reads of a stored body (`readRows`) judge it the way a save does (`withoutSpecialNodes`), and `sameDoc` (the one comparison, used by the Save button, the draft, the unsaved-changes warning and the server) ignores what the editor fills in on its own (`textDirection:"ltr"`, a variable's `required`/`hideDefaultValue`, a link's `rel`/`class`/`isUrlVariable`), so writing a letter and deleting it, or removing a block and putting it back, is no change. A document equal to the default is not an edit (the row keeps `doc` NULL and the legacy email goes out). A row in the old shape (a `title` column and a body with no blocks) is converted on reading by `convertOldShape`, in the server and in the editor, so there is one way to compose; one with only a title column keeps the email it had, with the default's first line UNDER the title as a paragraph (a snapshot of the old composer's output pins it). A document saved with the kicker's words as the first PARAGRAPH is not converted: it stays a paragraph under the title. A button or a link card whose variable holds no address for that client (a `{{…}}` href that comes out empty) is taken out of the email, never left pointing at `#`; an address that starts with a variable and goes on is treated the same way. Variables (`{{first_name}}`, `{{service}}`…) are the ones the catalogue lists for that key, are escaped, and an unknown one comes out empty. `{{date}}` and amounts are whatever the caller passes; formats are not unified.
- `app/emails/defaults/` holds the default text of each message and language (`defaultContent`: `doc` is the whole email, with its kicker (none for the consent request) and title and every block placed where the legacy email prints them, the closing sentence between the blocks before it and the one after it). It is what the editor opens on, what "reset" restores and what a row with no body of its own sends. A guardian test (`defaults.test.ts`) renders every legacy template and compares it, in strict order (preheader, kicker, title, text, blocks, closing sentence: no exception), with the defaults and the blocks: change a legacy email and it fails until the default follows. A second test checks every block against the legacy HTML.
- **The editor** (`messages/email/message-editor.tsx`): one Tiptap editor (Maily's) with two nodes of our own (`email-nodes.ts`, drawn by `email-node-views.tsx`): the title as an editable heading and each block as a dashed card that can be dragged, moved with Up and Down or removed. `EmailDocGuard` refuses any change that removes or doubles the title, or doubles or nests a block. When the document lacks a required block, an alert over the editor names it (with an Add button) and Save is disabled. The toolbar over the body (`body-toolbar.tsx`) holds the variables (an icon and a colour by kind, `variable-kinds.ts`) and puts back any removed block; the subject and the preheader stay as fields. The document is sent as plain JSON (`plainDoc`): the editor's attributes have no prototype, and a Server Action turns those into opaque references. The local draft is version 2.
- **Safety of the admin's body** (`app/lib/messages/safe-doc.ts`, pure): saving rejects (`findForbiddenNodes`, read with the top-level title and blocks swapped for empty paragraphs so paths keep their indices) and sending removes (`sanitizeDoc`) anything outside an ALLOW-LIST of node and mark types (the renderer dispatches any `type` that is a method of its class: `{"type":"render"}` never returns), the raw-HTML block, `doc` anywhere but the root, links that are not `https`/`http`/`mailto` (and images that are not `https`/`http`), and style attributes that are not a number or one of the editor's words. A link that is a variable is resolved and checked at send time. The editor (`components/dashboard/maily-editor.tsx`) does not offer the raw-HTML block, but the server is the real defence.
- `app/lib/messages/schema.ts` validates a save and is server-side: never import it from a client component. Saving goes through `saveMessageTemplate` (admin only), which refuses unknown variables, forbidden nodes and a WhatsApp template that cannot be sent.

### WhatsApp to the client

Two instant notices to a client about her own booking: the confirmation (`booking_confirmed` after a staff confirmation, `booking_paid` after the FIRST online payment). The reminder and any other timed notice are NOT here: they are appointment campaigns (see Email Campaigns, kind `appointment`), and `booking_reminder` is no longer a message that can go out on WhatsApp (`whatsappEligible: false`), so a client never gets two reminders. They go on the Meta template the admin chose on the message's page in Settings (the WhatsApp row of the Automatic messages card): a `message_templates` row with `channel = 'whatsapp'` for that key and language (`whatsapp_template_id` + `whatsapp_params`, resolved with the same field/static sources as campaigns). Code: `app/lib/whatsapp/notify-client.ts` (events), decision in `client-decision.ts`. Rules:

- They are TRANSACTIONAL, so the gate is `whatsapp_opted_in_at` (never the marketing consent), no `whatsapp_opted_out_at`, no `whatsapp_unreachable_at`, a number the database would accept, and the number NOT on `whatsapp_suppressed_phones` (a list that cannot be read means nothing is sent). The number is the CONTACT's (`clientPhone`), the one her consent belongs to and the one the appointment campaigns use, NEVER the one typed on the booking: anybody can type a client's address with another phone, and that number would get her name and her consent. A contact with no valid number gets no WhatsApp. Only keys with `whatsappEligible` in the catalogue qualify (the two above). The consent line of the booking form promises "the confirmation and the reminder of my appointment", which is what the appointment campaigns use as well.
- The WhatsApp switch is the row's `enabled` and does not depend on its being set up (on with no template still reads "Not set up: nothing is sent"). In the list, a WhatsApp row with NO template saved in any language (`hasTemplate` false) has its switch DRAWN off and locked (`aria-disabled`, with the reason in its name and in a tooltip): nothing is written to show it; with a template the switch is live and shows the saved `enabled`. The list's columns are State (the switch, first), Message, Type and Content (default / customised / not set up). Off, nothing is sent and ONE `skipped` entry says the message is off, but only for a client who would have been messaged (consent, a number, not on the STOP list) and not the configuration `skipped` below.
- With no saved WhatsApp row, or no consent, nothing is read further and nothing is written (a history row per booking without consent would bury the real ones). A template that cannot be sent (not approved, wrong language, parameters that do not add up, a URL button with a variable) leaves ONE `skipped` entry in the booking's history with the reason: that is a misconfiguration the admin must see.
- Sent and failed notices are recorded in the booking's history (`booking_events`, channel `whatsapp`) and the webhook advances them `sent → delivered → read`. Nothing here ever throws into the booking or payment flow, and every caller awaits it LAST.
- `bookings.whatsapp_reminder_sent_at` (from the retired fixed WhatsApp reminder) is OBSOLETE and unused; it stays in the database, no DDL.
- The language is the caller's when it states one, else the contact's `preferred_language` (its column default is `en`), else Spanish. So a WhatsApp row and an approved template are needed for EACH language that clients have.
